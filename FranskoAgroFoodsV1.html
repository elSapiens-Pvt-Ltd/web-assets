Process 2 — Route Classification & Geo-Mapping
Two-layer approach: Layer 1 uses shop GPS coordinates to auto-suggest geographic clusters — admin reviews and confirms each cluster as a named route with a vehicle type. Layer 2 uses Google Maps to find the optimal delivery sequence within each confirmed route.
Stage 2.1 · Layer 1 Admin-Assisted Clustering — Route Formation
How It Works

System uses shop lat/lng to auto-suggest geographic clusters. Suggestions appear on map for admin review — not saved until confirmed. Admin's ground knowledge always overrides the algorithm.

Admin Workflow
  1. All shops appear on map as ungrouped pins
  2. Admin triggers "Suggest Routes" — system draws colour-coded cluster zones
  3. Admin reviews: drag pins between clusters, split or merge zones as needed
  4. Admin names the route and assigns vehicle type (Small / Large) Assumed — Confirm OQ 2
  5. Route saved. Shops formally assigned
Map View
  • Colour-coded pins and translucent zone polygons per cluster
  • Unassigned shops highlighted separately
  • Click any pin: name, contact, outstanding balance, last order date
  • Filter by route, vehicle type, shop status
  • New shop added later — system suggests nearest route; admin confirms or overrides
Stage 2.2 · Layer 2 In-Route Sequencing — Google Maps Optimisation Sales = Delivery Route? — Confirm OQ 3
How It Works

Once shops are assigned to a route, system sends all lat/lng coordinates to the Google Maps Directions API with waypoint optimisation. Returns the most time-efficient visit order based on actual road distances — not straight-line. Admin can manually reorder any stop if needed.

What the Optimised Route Shows
  • Route line on map — connected path through all shops in sequence
  • Stop number, estimated travel time per leg, and total route duration
  • Order at each stop — items and quantity from that day's approved proformas
  • Sequence saved as standard delivery order; driver receives it on dispatch day
  • API limit: max 25 waypoints per request — larger routes auto-split into segments and stitched together

Process 3 — Order Taking (Telecaller) OQ 6 — Telecaller count & infra to confirm
Stage 3.1 Pre-Order Checks — Shop History Visibility
Purpose

Before a telecaller accepts any order, the system must surface the full financial and purchase history of that shop. Taking an order from a shop with a pending unpaid bill — or a history of delayed payments — directly creates a loss for the business. The system makes this information unavoidable at the point of order entry.

Information Displayed to Telecaller Before Order Entry
  • Outstanding balance — total amount currently unpaid by this shop
  • Previous order summary — date, items, value, and payment status of the last order
  • Item-wise purchase history — what products the shop has ordered, in what quantities, over time
  • Payment discipline — how quickly this shop has paid historically: average payment days and any delayed payments flagged by amount and duration
  • Credit limit — the maximum credit exposure approved for this shop
  • Shop status — Active, Inactive, or Blacklisted
Stage 3.2 Order Gate — Eligibility Criteria
Automatic Blocks — Order Cannot Be Created
🚫
Previous bill still pending — if the shop has one or more unpaid bills from a prior order, no new order can be raised. The outstanding must be settled first.
🚫
Order value exceeds credit limit — if the new order value would take the shop's total exposure above its approved credit limit, the order is blocked.
🚫
Shop is Inactive — orders are not accepted from shops marked as inactive.
🚫
Shop is Blacklisted — orders are permanently blocked. Cannot be overridden at telecaller level.
⚠️
Poor payment discipline — system flags the order for mandatory review if the shop has a pattern of late payments, even if technically within credit limit. Telecaller must acknowledge the flag before proceeding.
🚫
Shop score — Watch band (0–20) — orders from Watch-band shops are blocked for standard telecaller flow. Every order requires mandatory accounts team approval before a proforma can be saved.
⚠️
Shop score — Bronze band (21–35) — order is flagged. Telecaller sees the Bronze score and must acknowledge before proceeding. Proforma goes to accounts with a score-based review flag attached.
✅
All criteria met — no pending bills, within credit limit, shop is active, payment discipline acceptable, and score is Silver or Gold. Telecaller can proceed to create a proforma.
Stage 3.3 Proforma Creation
What the Telecaller Creates
  1. Telecaller takes the order from the shop — the shop is already mapped to a pre-existing route in the system
  2. System confirms the shop has passed all eligibility checks (enforced automatically — telecaller cannot proceed if any check fails)
  3. Enter item-wise order quantities — product, pack size, quantity
  4. System auto-populates: shop's route, vehicle type required, applicable pricing (GST or non-GST)
  5. Save as Proforma — this is a proposed order, not yet confirmed
  6. Proforma is sent to the Accounts Team for approval
Proforma Contains
  • Shop name, contact, address, and route
  • Item-wise order details: product name, quantity, unit price, line total
  • GST applicability (auto-applied based on shop master)
  • Total order value
  • Outstanding balance of the shop at time of proforma creation
  • Telecaller name and timestamp

Process 6 — Weighbridge OQ 7 — Purpose, ownership & location to confirm
Stage 6.1 Weighbridge Recording
Purpose
Open Question (OQ 7) — Need to confirm from Business Owner: Is the weighbridge company-owned or a third-party facility? Is it used only for outgoing dispatch, or also for incoming stock receipt? Who operates it? Answers will determine whether this is an internal system entry screen or an externally managed step.

The weighbridge records the weight of the vehicle before and after loading to establish the net weight of goods dispatched. This figure is used for billing accuracy, load compliance, and reconciliation of delivered goods.

Weighbridge Steps
  1. Before loading — vehicle enters weighbridge empty. System records Tare Weight (weight of empty vehicle)
  2. Vehicle moves to loading bay. Goods are loaded as per dispatch list
  3. After loading — vehicle returns to weighbridge fully loaded. System records Gross Weight (vehicle + goods)
  4. System calculates Net Weight = Gross Weight − Tare Weight
  5. Net weight is recorded against the vehicle number and dispatch record
  6. Both weighbridge tickets (before and after) are attached to the dispatch record
⚠️ SOP — Strict Compliance Required
  • No persons are permitted to be inside the vehicle during either weighing event
  • Driver and all loading staff must exit and stand clear before the reading is taken
  • Any weighbridge reading taken with personnel inside the vehicle is invalid and must be repeated
Data Recorded Per Vehicle
  • Vehicle number
  • Route — which route this vehicle is dispatched on
  • Date and time of each weighing event
  • Tare weight — empty vehicle weight (before loading)
  • Gross weight — loaded vehicle weight (after loading)
  • Net weight — goods weight (Gross − Tare, auto-calculated)
  • Loaded quantity — item-wise quantity actually loaded onto the vehicle
  • Difference — variance between the approved proforma quantity and the actual loaded quantity, if any; must be noted and signed off
  • Operator name — person who conducted the weighing
What Process 6 delivers
Visibilityevery kg dispatched logged against vehicle, route, and operator; full record of what left the warehouse Revenueinvoices reflect actual loaded quantity; no billing discrepancies or untracked shortfalls
Process 7 — Invoice Printing & Delivery
Stage 7.1 Invoice Printing — Process to Be Confirmed
⚠️ Open Question — When and Where Is the Invoice Printed?

The exact invoice printing workflow is not yet confirmed. Two possible approaches exist — the business needs to clarify which matches their actual practice before this stage can be finalised.

Option A — Printed at Depot Before Loading
  1. Accounts team scans the barcode on the approved proforma at the depot
  2. System converts the proforma to a tax invoice and prints it
  3. Printed invoice is physically placed with that shop's packed goods inside the vehicle before departure
  4. Driver carries pre-printed invoices — no printing needed at the shop
Hardware needed: Fixed or portable invoice printer at depot · Barcode scanner
Option B — Printed On-Site at Delivery (Likely)
  1. Delivery person arrives at the shop with the goods
  2. Opens the approved order on the handheld POS machine
  3. Invoice is printed on the spot from the handheld POS machine at the time of delivery
  4. Invoice is handed directly to the shop owner
  5. Payment is collected immediately after (cash or digital) — same device
Hardware needed: Handheld POS machine with built-in printer · carried by delivery person on route
Invoice Quantity — Proforma vs Final Loaded

The invoice quantity must reflect the final loaded quantity recorded at the weighbridge — not the original proforma quantity. If the weighbridge records a difference (e.g. 98 bags loaded vs 100 bags on proforma), the invoice is generated for 98 bags. The difference is logged and the proforma is updated before invoice generation. Route-wise dispatch must be confirmed at weighbridge before any invoice is printed.

Invoice Contains — Regardless of Option
  • Shop name, address, and GST number (if applicable)
  • Item-wise: product name, final loaded quantity, rate, line total
  • GST breakdown (where applicable)
  • Total invoice value
  • Vehicle number and route
  • Delivery date
  • Reference to approved proforma number
Stage 7.2 Delivery at Shop
At Each Shop on the Route
  1. Driver arrives at shop, confirms shop name and order
  2. Unload the correct goods for that shop
  3. Print invoice and hand to shop owner — either from a pre-printed copy (Option A) or printed on the spot from the handheld POS machine (Option B — to be confirmed)
  4. Collect payment if due (cash or digital) — using the handheld POS machine the delivery person carries on the route OQ 12 — Cash collection flow to confirm
  5. Record delivery confirmation in the system — timestamp and GPS location auto-captured
  6. Any rejected or returned items are noted on the delivery record

The detailed process for cash collected on delivery — how it is handed to the company, reconciled, and recorded — is an open question to be defined. See Open Questions section.

Call Log — What Is Recorded Per Interaction

  • Outcome — answered / not answered / visited in person / WhatsApp sent

Today's Follow-Up Queue

Each collection rep sees a daily queue — a list of shops that are due for follow-up today. This is auto-generated from scheduled follow-ups, promised payment deadlines that have passed, and shops that have been uncontacted beyond a set threshold. The rep works through the queue: calls, logs the outcome, and sets the next action. Nothing should end the day without a next state.

Stage 9.3 Follow-Up States — Every Shop Has a Current Status
Collection Status Values
Pending
Outstanding balance exists but no follow-up has been initiated yet. Starting state for all unpaid bills.
Scheduled
A follow-up date has been set. System will surface this shop in the queue on that date.
Callback
Shop owner asked to be called on a specific day. System shows this on the requested date and removes it from the queue until then.
Promised
Shop has committed to paying by a specific date. If payment is not received by that date, the system automatically moves this back into the queue as overdue.
Deferred
Senior person or owner has spoken with the shop directly and agreed to pause follow-up. No calls or reminders go out until the deferred date. Rep is notified not to call.
Escalated
Repeated contact attempts with no response, or payment promises broken multiple times. Flagged for owner or senior management to handle directly.
Collected
Payment received in full. Record is closed and removed from the active follow-up queue.
Rule: Every shop with an outstanding balance must always have a current status and a next action. A shop sitting in Pending with no follow-up date is a gap — the system highlights these as unactioned so they are never forgotten.
