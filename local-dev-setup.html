elSapiens Ecosystem — Local Development Setup#

A step-by-step guide for a new developer bringing the full elSapiens ecosystem up on a fresh Linux workstation (written against Ubuntu 26.04, kernel 7.x).

Work top to bottom — each section depends on the ones before it.

1. Overview#

The ecosystem is a set of independent backend services (Go, plus one NestJS service) and their React frontends. Services talk to each other over gRPC and share two database servers:

  • PostgreSQL — used by every service except accounts-api.
  • MongoDB — used only by accounts-api (person / entity / reseller records).

A local nginx reverse proxy maps friendly *.elsapiens.test hostnames to the Vite dev servers and backend APIs.

2. Prerequisites — tool installation#

2.1 PostgreSQL 18#

sudo apt update
sudo apt install -y postgresql postgresql-contrib postgresql-client postgresql-18-pgvector
  • Installs the server on the default port 5432, localhost-only.
  • postgresql-18-pgvector is required — the goods_services schema uses the vector extension (pg_trgm and pgcrypto ship with postgresql-contrib).

2.2 MongoDB 7.0#

Important: Do not install MongoDB 8.x on a kernel ≥ 6.19. MongoDB 8.x aborts on startup with a known TCMalloc/kernel incompatibility (SERVER-121912). Use the 7.0 LTS line, which predates that issue.

The 7.0 apt repo publishes up to Ubuntu 22.04 (jammy); that build runs fine on newer Ubuntu because glibc/openssl are backward compatible.

curl -fsSL https://www.mongodb.org/static/pgp/server-7.0.asc | \
  sudo gpg --dearmor -o /usr/share/keyrings/mongodb-server-7.0.gpg
echo "deb [ signed-by=/usr/share/keyrings/mongodb-server-7.0.gpg arch=amd64 ] https://repo.mongodb.org/apt/ubuntu jammy/mongodb-org/7.0 multiverse" | \
  sudo tee /etc/apt/sources.list.d/mongodb-org-7.0.list
sudo apt update && sudo apt install -y mongodb-org
sudo systemctl enable --now mongod

Install the shell separately (the mongosh snap is fine):

sudo snap install mongosh

2.3 nginx#

sudo apt install -y nginx

2.4 Node.js (via nvm) + pnpm#

Node is managed per-user with nvm, and pnpm is provided by corepack.

# install nvm, then a current Node:
nvm install --lts          # or a specific version, e.g. nvm install 26
# corepack ships with Node but on newer Node it must be enabled explicitly:
npm install -g corepack@latest
corepack enable
corepack prepare pnpm@latest --activate
pnpm --version

If corepack was installed by apt (node-corepack) and crashes with ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING, that apt package is too old for recent Node — remove it and use the npm-installed corepack as above.

2.5 Go + golang-migrate CLI#

sudo apt install -y golang-go        # Go 1.26+
# put go-installed binaries on PATH:
grep -q 'go/bin' ~/.profile || echo 'export PATH=$PATH:$HOME/go/bin' >> ~/.profile
source ~/.profile

# golang-migrate CLI — required to run migrations for elpos, elinventory,
# elcatalogs, elgeolocations:
go install -tags 'postgres' github.com/golang-migrate/migrate/v4/cmd/migrate@latest
migrate -version

2.6 AWS CLI (only for elmedia and elcatalogs)#

elmedia and elcatalogs upload files to S3 (bucket: elecosystem, region: ap-south-1) using the named AWS profile **dev-s3**.

sudo apt install -y awscli      # or: sudo snap install aws-cli --classic
aws configure --profile dev-s3  # enter the dev S3 access key / secret / region

Set region ap-south-1. Get the dev S3 credentials from the team — never commit them. Services read the profile name from their .env (AWS_PROFILE=dev-s3).

3. Database setup#

3.1 Create the currency PostgreSQL role#

Every service connects as the role **currency** (password currency). Create it once as the postgres superuser:

sudo -u postgres psql -c "CREATE ROLE currency WITH SUPERUSER LOGIN CREATEDB PASSWORD 'currency';"

Verify you can connect over TCP:

PGPASSWORD=currency psql -h 127.0.0.1 -U currency -d postgres -c "SELECT current_user;"

3.2 Create the databases#

export PGPASSWORD=currency
for db in app_registry elauth elaccounts geolocation goods_services elpos inventory_management media; do
  psql -h 127.0.0.1 -U currency -d postgres -c "CREATE DATABASE \"$db\" OWNER currency;"
done

3.3 Run migrations (build the schemas)#

Each service owns its schema via migrations. Run them per service:

ServiceCommandNotes
elauth*(automatic)*Runs on backend startup — AUTO_MIGRATE=true in .env. Also seeds the system reseller + admin login (see §6).
elmedia*(automatic)*Runs on backend startup (main.go).
elgeolocationscd elgeolocations && make migrate-upIncludes a migration that seeds country reference data.
elposcd elpos/backend && make migrate-up
elinventorycd elinventory/backend && make migrate-up
elcatalogscd elcatalogs/backend && make migrate-upLargest schema (~146 migrations).
elbookscd elbooks/server && bash scripts/reset_and_migrate.shNumbered SQL applied via psql. Override DB_USER=currency DB_PASSWORD=currency DB_PORT=5432 env vars (the script's defaults are stale).
elregistrystart the backend, then POST /v1/migrateMigrations run via an HTTP endpoint guarded by MIGRATE_SECRET_KEY from .env.

The make migrate-up targets call the migrate CLI under the hood — make sure §2.5 is done first. If a Makefile's default DATABASE_URL is stale, pass the correct one explicitly:

migrate -path ./migrations \
  -database "postgres://currency:currency@localhost:5432/<dbname>?sslmode=disable" up

3.4 MongoDB replica set#

accounts-api uses MongoDB transactions, which require a replica set — even a single-node one. Enable it once:

grep -q '^replication:' /etc/mongod.conf || \
  echo -e "\nreplication:\n  replSetName: \"rs0\"" | sudo tee -a /etc/mongod.conf > /dev/null
sudo systemctl restart mongod
sleep 2
mongosh --eval "rs.initiate()"
mongosh --eval "rs.status().myState"   # 1 = PRIMARY

4. Environment configuration#

Every service has a .env (gitignored) and a committed .env.example. For a fresh setup, cp .env.example .env in each service directory and adjust.

Key things to get right:

  • **DATABASE_URL** — postgres://currency:currency@localhost:5432/<dbname>?sslmode=disable. Port is 5432 (native install). The db name must match what you created in §3.2.
  • **MONGODB_URI** (elaccounts) — mongodb://localhost:27017/accounts. The key is MONGODB_URI (not MONGO_URI); the app and all seed scripts read that exact name.
  • gRPC addresses — services find each other via *_GRPC_ADDR=localhost:<port> entries. Use the gRPC ports from the table in §1.
  • **ALLOWED_ORIGIN / auth URLs** — use the canonical *.elsapiens.test hostnames (elinventory., elcatalogs., elauth., elaccounting., elpos.). Older .env files may still carry legacy names (inventory., goodsandservice., auth., elbooks.) — update them to the canonical form.
  • **AWS_PROFILE=dev-s3** — elmedia and elcatalogs only.

5. nginx reverse proxy + hosts file#

5.1 The hosts file#

Add the local domains to /etc/hosts so the browser resolves them to localhost:

Path: /etc/hosts

# elSapiens local dev
127.0.0.1 elauth.elsapiens.test admin.elsapiens.test elinventory.elsapiens.test elcatalogs.elsapiens.test elpos.elsapiens.test elaccounting.elsapiens.test
# append it (backs up /etc/hosts first):
sudo cp /etc/hosts /etc/hosts.bak.$(date +%F)
printf "\n# elSapiens local dev\n127.0.0.1 elauth.elsapiens.test admin.elsapiens.test elinventory.elsapiens.test elcatalogs.elsapiens.test elpos.elsapiens.test elaccounting.elsapiens.test\n" | sudo tee -a /etc/hosts > /dev/null

5.2 The nginx config#

The full reverse-proxy config lives in the repo at **scripts/elsapiens.test.conf**. Install it as an enabled nginx site:

sudo cp "scripts/elsapiens.test.conf" /etc/nginx/sites-available/elsapiens.test.conf
sudo ln -sf /etc/nginx/sites-available/elsapiens.test.conf /etc/nginx/sites-enabled/elsapiens.test.conf
sudo nginx -t && sudo systemctl reload nginx

Installed path: /etc/nginx/sites-available/elsapiens.test.conf (symlinked into /etc/nginx/sites-enabled/).

File structure: scripts/elsapiens.test.conf is one shared map directive (WebSocket upgrade for Vite HMR) followed by **six server blocks — one per *.elsapiens.test host**. Each host proxies / to its Vite dev server and /api (and /graphql where applicable) to its backend. The shape of one server block, for reference:

# from scripts/elsapiens.test.conf — one block per app

map $http_upgrade $connection_upgrade {   # WebSocket upgrade for Vite HMR
    default upgrade;
    ''      close;
}

server {
    listen 80;
    server_name elinventory.elsapiens.test;
    client_max_body_size 50m;

    location /api/ {
        proxy_pass http://127.0.0.1:11016;          # backend HTTP port
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /graphql {
        proxy_pass http://127.0.0.1:11016;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location / {
        proxy_pass http://127.0.0.1:31016;          # Vite dev server port
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 86400;
    }
}

6. Seeding the reseller + workspace#

After migrations, the databases have schemas but minimal data. elauth's migrations auto-seed the system reseller (elSapiens, is_ecosystem_owner=true, with the **fixed UUID 2092020e-bf8a-45d5-926c-7c6ec4ced657), the System Workspace** (00000000-…), and a reseller-admin login — elsapiensadmin / Admin@123.

The System Workspace has no domain by design — it's the platform's internal role container, not something you log into. You still need a real, domain-bound workspace for the elSapiens reseller; that's what this 3-script chain creates. Full reference: elaccounts/backend/SEED_GUIDE.md.

Easiest path — the interactive wizard#

You usually don't need to run the three scripts by hand. The wizard does it all:

bash elauth/backend/scripts/seed-ecosystem.sh

(Runs from any directory — it resolves its own location.) It runs all three scripts in order, carries the IDs between steps automatically (Step 1's person_uuid/org_entity_uuid → Step 2; Step 2's workspace_id → Step 3), and prompts for every value with help text and a dimmed [default] — Enter accepts, type to override. It needs only the databases running (not the backends), and finds the elaccounts repo via ELACCOUNTS_BACKEND_DIR in elauth/backend/.env. If the wizard works for you, skip the manual steps below and jump to "After seeding".

The manual steps below are what the wizard automates — use them only to run a single step by hand, seed a non-default reseller, or understand the data flow.

Manual — the scripts run in order:#

Script 1  elaccounts/backend  seed-reseller-full.ts             → person_uuid, org_entity_uuid
Script 2  elauth/backend      scripts/seed_workspace/main.go    → workspace_id
Script 3  elaccounts/backend  migrate-add-workspace-to-person.ts  (links it in Mongo)

Step 1 — reseller person + entities (MongoDB)#

cd elaccounts/backend
pnpm install            # first time only
pnpm seed:reseller:full

The RESELLER_CONFIG block at the top of scripts/seed-reseller-full.ts already defaults to elSapiens Admin / business@elsapiens.com — which is what elauth's migrations expect. **Do not change the fixed RESELLER_PERSON_UUID. Note the printed person_uuid and org_entity_uuid**. (It also prints a reseller_short_id — that's the Mongo-side id, informational only; the next steps do not use it.)

Step 2 — workspace (elauth / PostgreSQL)#

Edit the seedConfig block in elauth/backend/scripts/seed_workspace/main.go:

FieldValue
PersonIDperson_uuid from Step 1
ResellerID**2092020e-bf8a-45d5-926c-7c6ec4ced657** — the fixed reseller UUID from elauth migration 000002. Not the Step 1 reseller_short_id. elauth keys reseller_id on the UUID everywhere (migrations 000015/000018, the frontend .env).
OrgEntityIDorg_entity_uuid from Step 1
WorkspaceDomains**[]string{"elsapiens.test"}** — *required*. elauth resolves a workspace by domain; without this, login and registration cannot resolve the workspace and fail. The root-domain fallback means every *.elsapiens.test subdomain resolves here.
WorkspaceNameanything, e.g. "elSapiens Workspace"
Username / Passwordleave empty — you log in as the migration-seeded elsapiensadmin

Then:

cd elauth/backend
make seed-workspace

Note the printed **workspace_id**.

Step 3 — link workspace to person (MongoDB)#

cd elaccounts/backend
HANDLE=business@elsapiens.com \
WORKSPACE_ID=<workspace_id from step 2> \
RESELLER_ID=2092020e-bf8a-45d5-926c-7c6ec4ced657 \
IS_OWNER=true \
pnpm migrate:add-workspace

RESELLER_ID is the same fixed reseller UUID used in Step 2 — keeping reseller_id consistent across both databases. All three scripts are idempotent.

After seeding#

  1. Start the elauth and accounts-api backends — both must be running for sign-in to work (elauth calls accounts-api over gRPC; see §9).
  2. Open http://elauth.elsapiens.test — this only resolves if **§5 (nginx + /etc/hosts) is done**.
  3. On the sign-in screen choose More options → Username + Password.
  4. Sign in:
  5. with the migration-seeded reseller-admin **elsapiensadmin / Admin@123**, or
  6. if you set a custom owner username/password during seeding (the wizard's optional Step 2 prompt), use those instead.

7. Running the apps#

Prerequisite — do §5 first. The apps are reached via *.elsapiens.test hostnames, which only resolve once the nginx reverse proxy is installed and the **/etc/hosts** entries are added (§5). Before you start elauth or *any* frontend, confirm:

  • /etc/hosts has the six *.elsapiens.test entries (§5.1), and
  • the nginx site is installed + enabled and sudo nginx -t passes (§5.2).

A quick check: curl -I -H 'Host: elauth.elsapiens.test' http://127.0.0.1/ — a 502 is fine (means nginx routes correctly, upstream just isn't up yet); a connection refused or the default nginx page means §5 isn't done.

For each backend (Go services):

cd <service>/backend     # or <service>/server for elbooks, <service> for elgeolocations/elmedia
go run .                 # or: make run / make dev

For each frontend:

cd <service>/frontend    # or /client, /frontend-admin
pnpm install
pnpm dev

Then open the matching http://<app>.elsapiens.test URL. Recommended startup order (because of gRPC dependencies):

  1. elregistry, elgeolocations, elmedia, elaccounts (leaf services)
  2. elauth (depends on registry + accounts)
  3. elcatalogs, elinventory, elbooks, elpos (depend on auth + others)
  4. Frontends last.

9. Gotchas & known issues#

  • Login needs accounts-api running. During sign-in, elauth calls ResolveWorkspaceAccess on accounts-api over gRPC. If elaccounts is down, sign-in fails with a misleading "you don't have access to this workspace" — that's really a gRPC connection failure, not an authorization problem. Always start elaccounts before testing elauth login.
  • **The seeded admin login is a *username*.** elsapiensadmin is a username-type identifier — sign in with the Username + Password method. For that option to appear, the workspace's tenant config must include username_password in registration.user.allowed_login_methods. The seed_workspace script's config blob includes it; if you hand-edit a workspace config (e.g. via the admin Domains UI), keep it.
  • One domain ↔ one workspace is code-enforced only. AddDomainToWorkspace blocks adding a domain that's already on another workspace, but there is no DB unique constraint on workspaces.domains. A duplicate introduced via direct SQL or the seed script makes GetActiveWorkspaceByDomain (a :one query) return an arbitrary row. Never assign the same domain to two workspaces.
  • **/admin/* routes have no backend role check (pending).** The admin API routes are JWT-authenticated but not role-gated server-side — the reseller_admin gate currently lives only in the frontend-admin app. Adding server-side enforcement is tracked work.
  • Three workspace-creation paths, not identical. Client registration and the admin-UI "create workspace" both go through WorkspaceService.CreateWorkspace → defaultWorkspaceConfig(). The seed_workspace script is a one-time bootstrap and carries its own config blob — that divergence is expected (seed = initial setup), but be aware the seed-created workspace's config will not be byte-identical to a registration-created one.
